## 设计演变与被替代的方案

旧方案出现于不同阶段，不能概括为旧文档全部只支持批量上传：`8cd801f` 的总体架构已提出增量上传，但要求页面先经用户接受，并把最终排序列在服务端职责中；同阶段 Android 里程碑以“独立整理页 → 本地草稿”为中心。对话中还曾提出“整理后统一上传”。以下表格记录它们如何收敛。

| 主题 | 早期设想或旧文字 | 当前有效决定 | 当前实现与后续差距 |
|---|---|---|---|
| 相机与整理 | 拍完进入正式整理页，再确认草稿 | 目标相机页直接承担候选管理，完成后返回同一文档任务 | 当前仍进入整理网格；目标流程不强制经过该网格 |
| 页面接受与上传 | 旧总体方案要求页面经用户接受后进入上传队列；对话曾提出统一上传 | 有效上传载荷就绪后逐页提交，最终确认与上传解耦 | 当前完全本地；载荷规格和上传层待实现 |
| OCR 时机 | 已提过可增量解析，但与交互、最终提交关系不完整 | 服务端成功接收即排 OCR，不等全部拍完 | 独立 OCR Worker 已有，页面业务队列未接入 |
| 页序职责 | 总体架构和模型评测把“页面排序”作为编排能力 | 最终输入严格遵循用户确认顺序，VLM 恢复跨页逻辑 | 本地数组页序已实现，跨端约束待接入 |
| 完成与上传快照 | 保存整理结果，未来上传时生成不可变快照 | 图片可提前上传，最终冻结引用集合、顺序及有效版本 | 当前“完成”只导航；未来会话提交不等于 XML 方法调用 |
| 草稿何时保存 | 点击完成后生成草稿 | 每次页面事实变化自动保存；完成不再是首次落盘时点 | 当前 JSON 与文件已实现 |
| 持久化技术 | `SavedStateHandle` 曾被考虑用于草稿，数据库方案曾待选 | 私有文件 + `AtomicFile` JSON；UI 选择与草稿事实分离 | 未引入 Room/DataStore/WorkManager；未来上传扩展待定 |
| 草稿目录 | 早期实施计划提出新草稿使用独立目录 | 当前单草稿共用专用 `files/scan_draft`，清理后重建新的 draftId | 不宣称已存在按 draftId 隔离的多目录机制；旧 `files/captures` 不导入不清理 |
| 删除交互 | 所有页面两次点击删除叉确认 | 相机候选及其大图双击永久删除；整理页保留两步确认 | 两种交互已实现，不能混写成全局统一规则 |
| 重拍 | 新照替换原位置 | 当前先清理旧文件、留下重拍占位，再以相同 ID 接收新照 | 中断保留占位；联网后还需内容版本防串结果 |
| 进程死亡 | 早期文档将拍摄中进程恢复排除在里程碑外 | 恢复已经落盘的文件，不恢复未完成的真实快门 | 本地恢复已实现，上传与服务端任务恢复未实现 |
| 保存、退出和放弃 | 所有草稿未上传，可以仅考虑本地清理 | 当前仍成立；联网后必须考虑已上传页与远端会话 | 后台暂停、放弃会话和远端回收待讨论 |
| 动态配色 | 初始工程支持 Android 动态配色 | 固定黑蓝主题，跟随系统浅深色，辅助色限定状态用途 | 已实现，仅影响 Android，不影响 XML/Renderer |

## 当前本地功能细节

相机使用真实 JPEG，不将预览截图作为原图；请求约 5MP、4:3，设备实际输出由 CameraX 决定。EXIF 旋正与长边 1280 派生图在后台完成。最多接受 3 个尚未完成原图落盘的任务，安全原图落盘后释放名额，归一化串行执行。1280 像素与模型的 1280 image tokens 是不同概念。

相机取景框不受候选数目影响。竖屏 3:4、横屏 4:3；黑色剩余区域与覆盖层共同承载控件。快门在底部中央，完成按钮在右侧，圆角方形候选横排在快门上方。顶部只留返回，不再展示“相机能力测试”“已拍 N 张”“保存中”或性能数据。内部诊断仍可用于开发。

### 编辑和返回矩阵

| 所在位置 | 查看与删除 | 排序、重拍与返回 |
|---|---|---|
| 相机候选条 | 单击进入该候选的大图；双击永久删除 | 长按拖拽，松手持久化；相机返回时有页面/已接受拍摄则到网格，否则回宿主 |
| 相机候选大图 | 单页预览，双击删除 | 返回相机；当前不是整理页的左右滑动 Pager |
| 整理网格 | 自适应缩略图和页码；点击查看，两步删除叉确认 | 长按排序、继续拍摄、重拍；有删除确认时返回先取消确认 |
| 整理大图 | 左右滑页，使用同样的两步删除规则 | 返回先取消删除确认，再回网格 |
| 整理页退出 | 返回弹窗可保存、放弃或继续编辑；保存按钮可直接退出 | 当前返回临时宿主首页，尚无正式文档任务页 |

重拍先等待旧任务安全收束，保留 ID/位置并立即尝试清理旧图；取消、失败或进程中断继续显示占位。准备重拍期间全局串行并禁用整理操作与返回。删除最后一页留下空态，允许继续拍摄但禁用保存，离开或下次初始化清理空草稿。

文件恢复按实际可解码文件判定：有效原图和派生图恢复可用；只有有效原图时重建派生图；原图缺失或损坏时保留失败位置；重拍占位保留。丢失 postview 不算丢失照片。清单、路径、页序、恢复与迟到回调约束见 [草稿恢复](android_scan_draft.md) 和 [相机架构](android_camera_architecture.md)。

### 主题与原型设计

黑、白、中性灰和蓝构成主体，参考简洁的对话产品信息层级。蓝色使用 `#5595D1 / #A9C9FF`；红色 `#E97A7A / #FFBEC2`；黄色 `#E5C679 / #FFEEBC`；绿色 `#55967E / #B4DBCA`。完整 Material 3 与状态色映射集中在 [Android 视觉主题](android_app.md#android-视觉主题基线)。

本轮已关闭动态配色，但“映射完成”不代表所有前景背景组合已经通过可读性检查。尤其现有中性蓝灰深色容器搭配近黑前景需在 UI 原型评审中检查；本次仅记录现状，不调整颜色代码。

用户希望先参与原型设计，再逐步真机验收。Android Studio 可以使用现有相机和整理页 Preview 比较空态、多页、处理中、失败、删除确认与深浅色；预览不会调用真实相机、持久草稿或服务器。具体步骤见 [原型预览](android_env.md#android-studio-原型预览) 和 [真机部署](android_env.md#通过-android-studio-部署)。本地 UI 不依赖 Gradio；Gradio 已启动不等于 Android 已联通 OCR 服务。

## 后续工作与依赖

以下是开发依赖，不是时间承诺，也不要求先部署聊天模型才能评审扫描 UI。

| 工作 | 前置条件 | 可验收产物 |
|---|---|---|
| UI 原型评审与真机检查 | 现有 Preview 和 Debug App | 确认稳定取景、手势、返回、恢复、可读性；逐项记录结果 |
| 联网契约设计 | 明确本次 Pipeline 的既定约束 | 确定载荷、鉴权、版本、最终提交、保存/放弃和恢复语义 |
| 逐页上传与 OCR 队列 | 上传契约和页面识别接口就绪 | 页面可独立上传、重试、绑定有效版本结果，排序不重跑 OCR |
| 宿主任务与状态界面 | 工具上下文和任务状态契约 | 完成采集后回同一任务，显示真实阶段；原型可先用模拟状态 |
| 正式组装与导出 | 最终列表协议、有效 OCR、VLM 调度及预算 | 按序生成校验通过的 C2D-XML，并由 Renderer 输出 |
| 端到端与异常验收 | 上述链路接通 | 删除、重拍、乱序、离线恢复、重复提交和失败场景有独立证据 |

尚需讨论的问题集中维护在 [Pipeline 待决策表](capture_pipeline.md#6-联调前必须完成的决策)。自动裁切、透视矫正、视频取帧、相册导入、聊天 Provider、账号与跨设备同步仍属于后续能力。本地单草稿和旧整理页的产品迁移要随会话设计明确，不能只增加一个上传调用便宣告完成。
