## Issue 1：Worker 心跳缺少存活检测闭环

- 状态：待修复
- 记录日期：2026-09-07
- 相关代码：[Worker.serve](../server/src/capture2doc/service/worker.py)、[Repository.heartbeat](../server/src/capture2doc/service/repository.py)、[健康检查接口](../server/src/capture2doc/service/api.py)

### 当前行为

Worker 通过独立后台线程，每隔约 5 秒向数据库更新 `runtime` 表中的 `worker_heartbeat` 时间戳，用于记录进程存活状态。心跳写入失败时记录异常日志，随后继续尝试。

目前代码仅实现心跳写入，缺少对应的读取、超时判定和异常处理机制。现有 `/internal/health` 接口仅执行数据库 `SELECT 1`，未检查 Worker 心跳。

### 影响与边界

心跳机制仅完成状态上报，尚未形成存活检测闭环。当 API 正常运行而 Worker 已停止时，现有健康检查仍可能返回 `ok`，无法据此识别后台任务无人处理的状态。

心跳由独立线程维护，因此时间戳正常更新也不能保证主线程的任务调度或模型推理正常推进。Worker 存活检测与任务进度检测应分别定义。

### 后续修复方向

1. 增加心跳读取与可配置的超时判定，明确尚未产生心跳、正常和过期三种状态，以及启动宽限期。
2. 将 Worker 状态接入适当的健康检查或监控入口，区分 API、数据库和 Worker 的状态，并明确异常时的告警或恢复策略。
3. 如需识别推理卡住，另行设计任务进度或执行超时检测，不能仅依赖线程心跳。

### 验收要点

- Worker 正常运行时，读取方能够识别新鲜心跳。
- Worker 未启动或停止更新后，读取方能按约定报告缺失或超时状态。
- API 和数据库正常、Worker 异常时，监控结果能够区分这些状态。
- Worker 恢复心跳后，状态能够恢复正常。
- 不将心跳正常等同于模型推理或任务处理正常。
