本文记录 Android 相机模块当前已经实现的职责、数据流和状态管理方式。具体拍摄参数与选型理由见 [Android 相机拍摄与图像处理](android_camera_capture.md)，自动化测试和真机验收方法见 [Android 相机测试与验收](android_camera_testing.md)。

## 功能边界

当前相机模块承担拍摄与归一化核心链路，并把有序页面持续写入本地草稿：

```text
运行时权限 → CameraX 会话 → 稳定 4:3 取景区 → 接受快门
          → 预占稳定 pageId → CameraX 真实拍照 → 原始 JPEG 落盘
          → 候选页立即可管理 + 后台生成最长边 1280 像素的 OCR 派生图
          → 本地有序扫描草稿
```

底层已经实现：

- 仅在用户进入相机功能后请求 `CAMERA` 权限；
- 后置摄像头预览和真实 JPEG 拍摄；
- 竖屏 `3:4`、横屏 `4:3` 的明确取景框；
- 连续拍照、单张任务状态和未落盘任务的队列上限；
- 点按对焦、物理方向监听和 EXIF 像素旋正；
- 原图与 OCR 派生图的 App 私有目录保存；
- 尺寸、文件大小、方向和分阶段耗时的内部观测。

本轮相机页已经按以下交互契约实现。2026-09-05 合并后的 JVM、Debug 构建、Lint 和设备测试 APK 构建检查成功；截至本轮记录，下列新 UI 交互尚未完成真机验收：

- 相机预览区尺寸保持稳定，候选图片和控制按钮全部叠加在预览之上，新增页面不得挤压取景区；
- 顶部只保留返回按钮，移除“相机能力测试”、已拍数量、保存状态、分辨率和耗时等调试文案；
- 快门固定在底部中央，“完成”位于右下方；候选页以圆角方形横排浮在快门上方；
- 候选页单击打开大图，双击立即删除，长按拖拽调整草稿顺序；页面处理状态只使用小型进度或失败图标表达；
- 原始 JPEG 已安全落盘即可参与“完成”，1280 派生图允许在后台继续生成；
- 当前“完成”先进入本地页面整理页，不上传、不触发 OCR，也不进入尚未实现的任务页。

尚未实现（本阶段外）：

- 文档边缘检测、裁切、透视校正、质量判断和去重；
- 相册导入、闪光灯、变焦、镜头切换、视频取帧和 ZSL；

扫描草稿与页面整理功能已在主流程中接入：

- 相机接受快门后先预占草稿页面，原图落盘后即可在候选区管理；
- 点击“完成”进入页面整理页，可继续拍摄、拖拽、重拍、删除和保存退出；
- 草稿元数据使用 JSON 落盘，可在配置变化与恢复场景下继续编辑。

## 组件职责

| 组件 | 当前职责 |
|---|---|
| `CameraProbeRoute` | 连接生命周期、权限请求、ViewModel 和 CameraX 会话 |
| `CameraProbeScreen` | 渲染稳定取景区、叠加式候选条、快门、完成按钮和候选大图 |
| `CameraPreview` | 创建 `PreviewView`，绑定 Preview 与 ImageCapture，监听物理方向 |
| `CameraSessionHandle` | 向上层暴露拍照能力、实际分辨率、postview 能力和点按对焦 |
| `CameraCaptureProfile` | 集中保存画幅、目标分辨率、JPEG 质量和队列上限 |
| `CameraProbeViewModel` | 管理相机门禁、瞬时拍摄任务，并观察/修改草稿页面事实 |
| `ScanDraftRepository` | 作为页面 ID、文件状态和顺序的唯一事实源，串行原子持久化 |
| `ImageNormalizer` | 采样解码、EXIF 变换、等比缩放和原子写入 |
| `CaptureArtifact` | 保存文件路径、尺寸、字节数、方向和耗时指标（内部产物） |

这些类型目前都属于 App 内部接口，不是稳定公共 API。

## 相机门禁状态

相机整体可用性由 `CameraGateState` 表示：

```text
PermissionRequired → RequestingPermission
                  ├→ PermissionDenied
                  └→ StartingCamera → Ready
                                      ├→ CameraUnavailable
                                      └→ Error
```

- 权限状态在首次进入以及 Activity `ON_RESUME` 时重新读取，用户从系统设置返回后可以恢复；
- 无摄像头设备进入 `CameraUnavailable`，不会阻止宿主 App 启动；
- CameraX 绑定失败进入可重试错误状态；
- 离开或重建预览时释放绑定，重新进入前台后重新建立会话。

## 单张任务状态

每次被接受的快门先在草稿中预占稳定 `pageId`，随后创建与该页面关联的瞬时 `CaptureJob`：

```text
Queued → Capturing → Saving → Normalizing → Ready
                                      └────→ Failed
```

任务保存页面关联、文件路径、阶段时间点、临时 postview、最终 `CaptureArtifact` 和可读错误信息。状态推进只允许向前；已经完成、删除或失败的页面不会被迟到回调重新插入。

`CaptureJob` 只用于当前进程内的相机回调和即时反馈。持久页面是否存在、页面状态及其顺序始终以 `ScanDraftRepository` 为准；进程重建时不恢复尚未完成的真实快门，只根据已落盘文件恢复页面。

相机状态和图片任务状态相互独立。某张图片保存或归一化失败时，其他任务以及预览仍可继续运行。

## 并发和背压

- 最多接受 3 个尚未完成原图落盘的任务；
- `Queued`、`Capturing` 和 `Saving` 计入拍照上限；
- 原图进入 `Normalizing` 后立即释放一个拍摄名额；
- 实时拍摄和恢复流程的归一化统一经过 Repository 级共享串行锁，避免同时解码或写入同一页面，并控制多张照片并行处理造成的内存和 CPU 峰值；
- 原图安全性使用受限尺寸的真实像素解码确认，不只读取 JPEG 头部尺寸；进程内缓存只记录已经验证成功的页面 ID；
- 队列满时只禁用快门，不遮挡或停止 Preview；
- 原始 JPEG 安全落盘后，该页面不再阻塞“完成”；后台归一化不占用完成门槛，派生图生成失败但安全原图仍存在时也可以进入页面整理；
- 仍在 `CAPTURING`、原图缺失或损坏、以及需要重拍的保留页面会阻止完成，并继续以状态图标呈现；
- 点击“完成”后停止接受新快门并进入现有本地页面整理页，不再展示旧的批次结果/性能页面。

这里的上限是进程内背压，不是持久化任务队列。

未来联网阶段由独立上传/任务层观察有效载荷并提交页面，成功接收后排入 OCR 队列。相机候选可见、原图安全、派生图可用和服务端接收是不同事件，不能在 postview 回调中宣称 OCR 已启动。稳定 `pageId` 还需与内容版本结合，最终提交冻结集合、顺序及有效版本；VLM 等最终所需 OCR 齐备后按序处理。现有快门门禁和归一化锁不承担网络调度；完整流程及未决协议见 [扫描 Pipeline](capture_pipeline.md)。

## 文件和数据边界

拍摄文件写入到本地扫描草稿目录：

```text
files/scan_draft/pages/<pageId>/
├── original.jpg
└── normalized_1280.jpg
```

- `original.jpg` 是 CameraX 保存的真实拍照结果，供后续重新处理；
- `normalized_1280.jpg` 是方向已旋正、最长边不超过 1280 像素的 OCR 派生图；
- 文件位于 App 私有持久目录，不进入系统相册，不需要存储权限；
- `scan_draft` 目录为单草稿隔离目录；放弃草稿会同步清理该目录；
- App 卸载时文件会被删除。
- `CaptureArtifact.normalizedPath` 保持通用命名，没有暴露具体 OCR 模型。

Android 只生成通用图片产物。OCR 模型的视觉 token、网格对齐和推理参数属于服务端边界，不进入相机状态模型。

`normalized_1280.jpg` 的存在不代表识别过文字。当前 `CaptureJob` 和 `ScanPageState` 仅表达本地采集处理，不添加未实现的上传、OCR 或文档任务状态。

草稿元数据模型、恢复规则与单草稿策略见：[Android 扫描草稿与恢复说明](android_scan_draft.md)。

## 生命周期限制

当前 `AndroidViewModel` 与应用级 Repository 支持旋转、Activity 重建、后台切换和进程重启后的草稿恢复：

- 草稿使用 `files/scan_draft/draft.json` 保存版本、创建时间、更新时间与有序页面；页面预占、原图落盘、归一化结果、删除、重拍和排序都会自动持久化；
- 清单写入在 `Dispatchers.IO` 上通过协程 `Mutex` 串行，并使用 `AtomicFile` 原子替换；页面数组是唯一页序来源；
- 应用重启后先校验清单与页面文件，并恢复 `READY` / `FAILED` / `RETAKE_REQUIRED`；Repository 已经初始化但相机 ViewModel 重建时，也会再次协调未完成页面恢复；
- 原图缺失或损坏的页面保留为失败占位；原图有效但派生图缺失或损坏时，通过同一 Repository 级归一化锁自动重建，失败则保留安全原图和 `FAILED` 状态；
- 同一时刻只允许准备一个重拍页面；准备期间整理页禁用返回、删除、排序和再次重拍，避免多个页面同时进入无对应相机入口的重拍占位；
- `SavedStateHandle` 只保存当前预览页面等 UI 选择，不保存草稿事实；正常切换场景下返回继续拍摄或编辑不丢页序和状态；
- 无有效清单时只清理专用 `files/scan_draft` 范围，不导入或删除旧 `files/captures` 内容；不再被清单引用的孤立页面目录在恢复时清理。

这些是本地恢复能力，不恢复上传请求或会话级最终提交。未来网络恢复还需要持久化/查询远端确认及有效内容身份，不能以 ViewModel 重建代替任务恢复。
