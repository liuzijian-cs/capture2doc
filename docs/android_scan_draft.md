# Android 扫描草稿与恢复说明

> 状态：本地扫描草稿闭环与相机候选交互已实现；最终本地构建检查通过，新 UI 真机验收待执行，未接入上传/会话提交
> 最近核对：2026-09-05；实现基线：`e55c8f8`

本页记录 Android 本地扫描草稿的事实模型、持久化约束与恢复规则。该内容不进入 C2D-XML。

本页的单草稿、整理网格和“尚未上传”均是当前代码事实。目标联网阶段不强制独立整理页，保存/放弃也涉及远端会话，不能原样套用；见 [扫描 Pipeline](capture_pipeline.md)。

## 草稿文件结构

草稿持久化路径：

- `files/scan_draft/draft.json`
- `files/scan_draft/pages/<pageId>/original.jpg`
- `files/scan_draft/pages/<pageId>/normalized_1280.jpg`

当前使用固定单草稿专用根目录；放弃后清理并创建新 draftId，不是每个 draftId 分配独立根目录。这是与早期计划的实现差异，不能据此推断已有多草稿隔离能力。

草稿元数据使用 `AtomicFile` 落盘。一次快门只有在通过相机门禁、真正被接受后才会先写入 `CAPTURING` 页面占位；队列已满或相机未就绪时的点击不会创建页面。占位并不表示快门已经完成，进程恢复只承认实际可解码的已落盘文件。

JSON 使用平台 `org.json`，没有第三方序列化库。Repository 在 `Dispatchers.IO` 上通过 `Mutex` 串行更新清单，对外以只读 `StateFlow` 发布草稿与错误，ViewModel 再映射 UI 状态；文件路径相对于草稿根目录。页面数组是唯一页序来源，没有额外 `order` 或“已完成后不可编辑”的持久状态字段。

### `ScanDraft`

- `schemaVersion`：当前固定为 `1`
- `draftId`：单草稿 ID
- `createdAtEpochMillis` / `updatedAtEpochMillis`
- `pages`：按顺序保存的页面数组

### `ScanPage`

- `pageId`
- `originalRelativePath`
- `normalizedRelativePath`
- `state`
- `errorMessage`

### 页面状态

- `CAPTURING`：已预占位，拍照尚未写完
- `NORMALIZING`：原图已入盘，OCR 派生图正在重建
- `READY`：本地图像处理完成；恢复时要求原图和派生图都可解码，不表示 OCR 已完成
- `FAILED`：页面处理失败；安全原图仍存在时可预览、可进入整理页并等待派生图重试，原图缺失或损坏时才必须重拍或删除
- `RETAKE_REQUIRED`：重拍占位

页面整理页对 `READY` 页面优先使用 `normalized_1280.jpg`，对 `NORMALIZING` 或保有安全原图的 `FAILED` 页面优先使用 `original.jpg`，两者均可相互回退。拍照页为了最快反馈，候选缩略图的显示优先级是当前进程 postview、已落盘原图、派生图；恢复后 postview 不存在，直接从文件重建。

## 规则：页面状态与恢复

应用重启/重建后：

- `pageId` 不变；顺序按 `pages` 数组顺序恢复
- `READY` 页面要求原图和派生图都可解码
- `CAPTURING` / `NORMALIZING` 页面若原图和派生图均有效，直接恢复为 `READY`；若只有原图有效则重建派生图，没有有效原图则保留原位置并转为失败占位，不尝试恢复真实快门
- 原图缺失或不可解码：置为 `FAILED`
- 原图可解码但派生图缺失或损坏：通过 Repository 级共享归一化锁自动重建派生图并恢复为 `READY`；重建失败则保留安全原图并变为 `FAILED`
- `RETAKE_REQUIRED` 保留占位，不主动重建
- “安全原图”必须通过受限尺寸的真实像素解码，不能只凭文件非空或 JPEG 头部尺寸判断
- 不再被当前清单引用的孤立页面目录会在下次恢复时清理；清单内原图损坏的页面不会被静默删除，而是保留原顺序并显示失败占位
- 清单缺失或损坏时只清理专用 `files/scan_draft` 范围，不导入或删除旧 `files/captures` 内容

## 单草稿策略

- 仅存在一个活跃草稿文件
- 放弃草稿时删除 `draft.json` 和全部页面目录
- 页面预占、原图落盘、归一化结果或失败、删除、重拍和排序完成后都会自动更新清单；拖拽只在松手时持久化最终顺序
- 页面数组位置是唯一顺序来源，不额外持久化 `order` 字段
- 删除最后一页后保留空页面提示并禁用“保存并退出”；离开流程或下次初始化时自动清理空草稿

## 进程与系统事件

- 旋转、Activity 重建、切后台和进程重启：以 `draft.json`、Repository 状态与文件存在性重建草稿视图
- Repository 已经初始化但相机 ViewModel 重建时，会再次恢复未完成页面；不尝试重放尚未完成的真实快门，只承认已经落盘且可恢复的文件
- `SavedStateHandle` 仅保存当前预览页面等 UI 选择；草稿、页面状态、页序和路径事实只来自 Repository 与清单
- 上传、服务端任务恢复不在本地草稿模块范围内

## 与 UI 的配合

- 拍照页候选条是当前草稿页面的即时视图：新增页追加到末尾，排序完成时持久化新顺序
- 拍照页候选单击打开单页大图、双击立即永久删除、长按拖拽排序；相机大图也支持双击删除，返回回到相机，不是整理页的滑页 Pager
- 页面整理页仍使用两步行内删除确认：第一次变灰并放大删除按钮，第二次确认；点击其他区域或返回取消
- 两种删除手势不同，但最终都调用同一仓库删除语义：先从清单移除，再尝试删除页面目录
- 重拍先协调旧任务，写入 `RETAKE_REQUIRED` 并立即尝试删除旧文件，再以原 `pageId` 和原位置接收新照片；失败、取消或进程中断时保留占位
- 重拍准备全局串行；准备旧任务和删除旧文件期间，整理页暂时禁用其他页面操作与返回
- 进入 Capture2Doc 时，无草稿直接进入相机；已有草稿则选择“继续草稿 / 放弃并新建”，取消弹窗时留在宿主 App
- 整理页大图返回网格；存在删除确认时，返回先取消确认。相机有页面或已接受拍摄时返回网格，否则返回宿主。网格返回退出时选择“保存并退出 / 放弃草稿 / 继续编辑”，网格保存按钮则可直接退出
- 拥有草稿时可继续编辑（支持再编辑、删除、重拍、拖拽）
- 拍照页“完成”只要求至少存在一页且所有保留页面都有安全落盘的原始 JPEG；派生图可以继续后台生成，派生图失败形成的 `FAILED + 安全原图` 也允许进入整理页。`CAPTURING`、`RETAKE_REQUIRED` 或无安全原图的 `FAILED` 页面会阻止完成
- 当前“完成”只进入本地页面整理页，不上传、不触发 OCR，也不执行 `finalize`

## 未来任务与服务端边界

本地 `pageId` 预留为未来跨端稳定页面身份，但当前版本不上传。已决定的目标语义是：

- 一个文档对应一个任务/对话/会话；
- 页面上传载荷就绪后按 `pageId` 幂等提交，上传成功立即进入该页 OCR 队列；原图或派生图作为具体载荷仍待联调阶段确定；
- 用户在相机候选管理中决定完成后发起最终集合、顺序与有效内容版本提交；当前网格不是目标必经步骤，排序不重新执行页面 OCR；
- 文档级 VLM 等待最终列表内各页 OCR 结束，再严格按该数组顺序处理；
- 已删除页面不进入最终列表，远端孤立文件由延迟清理策略处理。

这些会话、上传与 OCR 状态不写入 C2D-XML，也尚未加入当前 Android 草稿清单。

未来图片会早于文档最终确认上传，“上传快照”应理解为最终输入引用的冻结，而非整理结束才传全部图片。重拍虽然沿用 pageId，但旧内容的 OCR 不能成为新图的结果；版本和提交协议见 [Pipeline 待决策表](capture_pipeline.md#6-联调前必须完成的决策)。

当前“保存并退出”不会改变任何远端状态；未来已上传会话的暂停、恢复、放弃和孤立资产回收仍待设计。本地清理完成不能显示为远端删除成功。当前单草稿策略不等于未来只允许一个宿主任务，现有 JSON 模型也尚未包含上传恢复所需事实。
