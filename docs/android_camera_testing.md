## 既有基线已通过的基础自动化覆盖

### 尺寸和方向

- `4032×3024 → 1280×960`；
- `3024×4032 → 960×1280`；
- `800×600` 不放大；
- 奇数尺寸保持比例，舍入误差不超过一个像素；
- EXIF 0°、90°、180°、270° 均旋正到正确像素尺寸；
- 输出文件可解码，最终 EXIF 方向为正常。

### 拍摄配置和任务

- Preview、ImageCapture 和 postview 的 4:3 选择策略；
- 约 5MP 目标尺寸及“优先较低”的回退规则；
- 三个未落盘任务的队列上限；
- 回调乱序不会让任务状态倒退；
- 单张失败不破坏其他任务。

### Compose 状态

- 权限说明、请求中、拒绝、相机启动、就绪、无相机和错误重试；
- 拍摄过程中 Preview 与快门继续显示；
- 队列满时只禁用快门；
- 对焦框、缩略图和单张失败；
- 竖屏 `3:4`、横屏 `4:3` 取景比例；
- 取景框与控制区不重叠。

最后一项属于旧布局历史验收，已被新 UI 的“控件覆盖相机层但不参与 viewport 测量”取代，不能继续作为新版布局要求。新版用例已调整，仍需执行设备测试。

4. 分别准备含小字、表格、公式和低对比度内容的文档样本；

6. 测试期间保持闪光灯关闭，并记录系统自动旋转是否开启。

## 真机功能验收

### 权限与恢复

- 宿主 App 启动时不提前请求相机权限；
- 首次进入相机功能时显示用途说明并请求权限；
- 拒绝后页面可重试，也可引导至系统设置；
- 从系统设置授权并返回后能够重新绑定相机；
- 切入后台再返回时不会重复归一化已经完成的图片。

### 取景、对焦和方向

- 竖屏取景框为 `3:4`，横屏取景框为 `4:3`；
- 横竖屏均使用叠加在相机层上的顶部返回、候选条与底部操作区，不再使用横屏右侧控制栏；
- 候选条出现、追加、删除和排序前后，Preview 的位置与尺寸保持不变；
- Preview 内容完整，没有为了铺满屏幕而裁切；
- 点击近处和远处文字时，对焦框位置与触点一致；
- 对焦失败或仍在进行时可以继续拍照；
- 竖屏、左右横屏和反向竖屏照片方向正确；
- 系统旋转锁定开启和关闭时分别验证一次。

### 连续拍摄与文件

- 一秒内连续点击三次，三个请求都被接受；
- 第四个未落盘请求被临时限制，不覆盖已有文件；
- Preview 不因保存或归一化而消失；
- 每个最终进入 `READY` 的 `pageId` 对应目录同时存在 `original.jpg` 和 `normalized_1280.jpg`；派生图失败但安全原图仍存在时，页面可以暂时保持 `FAILED`；
- `READY` 页的两个文件均可解码，原图保持设备实际选择的 4:3 分辨率；
- 横向 OCR 图为 `1280×960`，纵向 OCR 图为 `960×1280`；
- 较小图片不放大，内容无裁切、拉伸或补边；
- 单张失败可以重试或移除，不影响其他照片。
- 保留尺寸头但截断像素数据的 JPEG 必须判为原图损坏，不能启用“完成”；

### 候选与页面整理

- 拍摄多页后，候选顺序与 `draft.json` 的 `pages` 数组一致；
- 点按候选进入对应大图，返回后相机和当前草稿保持不变；
- 双击同一候选立即删除本地页面，其他页面顺序连续更新；
- 长按候选拖拽，松手后重建 App 仍保持新顺序；
- 点击拍照页“完成”进入本地页面整理页，不触发上传、页面 OCR、`finalize` 或文档级 VLM。
- 快速点击同页或不同页的“重拍”时只能存在一个重拍准备任务，不能留下额外的 `RETAKE_REQUIRED` 占位。
- 相机候选大图双击删除并返回相机；整理网格的大图可左右滑页，返回先取消删除确认，再回网格；
- 整理页第一次点击删除叉进入行内确认，点其他区域或返回取消，再点同一叉永久删除；
- 重拍准备立即尝试清理旧图并保留原 ID/位置，取消、失败或中断后占位可再次重拍或删除；
- 最后一页删除后保持空态、禁用保存并可继续拍摄，离开后清理空草稿；有草稿再次进入时可继续、放弃新建或取消；
- 构造完整文件、仅有效原图、损坏原图、重拍中断四种状态，重建 Repository/ViewModel 后核对页序、失败占位和派生图恢复；
- 旋转和切后台后检查页面与草稿；进程恢复以已落盘文件为准，未完成快门不应被重放。

## OCR 输入对照

使用同一批含小字的页面比较最长边 1024 和 1280 两档派生图：

- 固定服务端模型、prompt、`max_pixels` 和生成参数；
- 记录 JPEG 体积、上传耗时、processor 的实际网格和 image tokens；
- 对比漏字、错字、表格结构、公式和阅读顺序；
- 同时记录首 token、总推理耗时和峰值显存；
- 根据质量与成本决定正式上传规格，不只比较肉眼清晰度。

当前 Android 默认采用 1280 像素长边；PaddleOCR 的 1280 image-token 档仍由服务端 `max_pixels` 控制。

既有 1024/1280 输入对照按用户确认记录完成，当前客户端派生图规格继续采用 1280 像素长边。本轮未重新执行对照，没有补录原始测量值。该结论不冻结未来网络上传载荷，原图还是派生图仍需联调决策。

| 场景 | 预期约束 |
|---|---|
| 连续拍摄时第 1 页先上传 | 接收成功即排 OCR，不等待全部拍完；不把排队显示成文档完成 |
| OCR 按 B、A、C 返回，最终选择 C、A | 严格按 C、A 组装；B 的失败不阻塞最终文档 |
| 已上传页面删除或仅排序 | 删除页不参与文档，排序不重复 OCR；远端回收按最终约定验证 |

| 仍有未上传页面时点击完成 | 不丢页、不假报成功；具体等待/提交行为在协议冻结后补齐断言 |
| 网络中断与进程重启 | 本地文件保留，上传确认/会话状态可恢复；不重放真实快门 |
| 已上传会话保存或放弃 | 不再统一提示“尚未上传”；本地和远端清理分别按协议确认 |
| 最终必需页 OCR 失败 | 明确失败或等待恢复，不能静默跳页生成完整成功文档 |
| 重复最终提交、重复模型响应 | 不重复创建文档或追加 XML；网络与模型轮次分别验证 |
| 模型资源与导出失败 | 阶段反馈真实，不把入队或 XML 字节生成当成目标格式已导出 |
