# Android App 产品与架构草案

> 状态：本地采集已实现；目标联网流程已决定但未实现；产品外壳与协议细节待讨论
> 核对日期：2026-09-05；实现基线：`e55c8f8`

## 文档目的

本文档记录 Android App 的产品定位、功能边界和工程组织。拍照页候选交互已实现；逐页上传、接收后排 OCR、最终页序提交的方向已决定，具体网络协议尚未冻结。跨端流程以 [扫描 Pipeline](capture_pipeline.md) 为准，早期方案与本轮成果见 [开发记录](android_progress_and_plan.md)。

## 产品定位

Android App 的主体是一个类似 ChatGPT 或豆包的对话式助手。用户以会话作为主要工作入口，通过文字、图片、文件或工具完成任务。

拍照/视频转文档不是整个 App 的首页主流程，而是工具系统中的一个独立功能。本文暂称该工具为 **Capture2Doc**：一次文档严格对应一个宿主 task/对话上下文和一个采集 session。工具负责采集页面、确认最终顺序、提交本地服务端解析任务，并把处理状态和最终文档返回同一 task/对话。

宿主 App 的最终产品名、助手能力范围及 Capture2Doc 是否继续作为仓库名，尚待确定。

## 产品结构

```text
宿主 App
├── 对话
│   ├── 会话列表
│   ├── 消息流
│   └── 输入区
├── 工具入口
│   └── Capture2Doc
│       ├── 拍照或视频取帧
│       ├── 拍照页候选确认、删除与排序
│       ├── 逐页上传与页面 OCR 队列
│       ├── 有序 pageId finalize 与任务进度
│       └── 文档预览与导出
├── 生成物
│   └── Lark 文档、Markdown 或思源 `.sy`
└── 设置
    ├── 助手与模型服务
    └── Capture2Doc 本地服务
```

目标联网流程中，用户从对话输入区的附件或工具入口启动 Capture2Doc。拍照页直接承担候选管理，不强制经过独立整理页。每页上传载荷就绪后幂等提交，服务端接收成功即排入 OCR 队列；用户仍可继续拍摄和编辑。点击“完成”发起最终集合、顺序及有效内容版本提交，并返回同一任务界面；服务端接受后冻结输入，等待所需 OCR 结果再启动 VLM。任务界面显示实际的等待上传/提交、OCR、组装、校验、导出或失败阶段，而不是统一显示“VLM 处理中”。

当前 Android 只运行本地扫描草稿与页面整理，相机“完成”仍进入整理网格，“继续草稿”也从该网格恢复。这个本地过渡导航不代表目标联网产品必须保留独立整理步骤。未上传页面与最终提交如何协调，见 [Pipeline 待决策表](capture_pipeline.md#6-联调前必须完成的决策)。

## 功能边界

以下是目标职责；实际接入状态见本文“当前实现状态”，不要据此假定所有功能已可用。

### 宿主 App

- 管理会话、消息、输入区和全局导航；
- 展示工具入口并管理工具启动与返回；
- 展示文件、图片和其他生成物；
- 管理聊天服务及工具服务的独立配置；
- 提供全局主题、权限解释、错误展示和设置入口。

### Capture2Doc 工具

- 管理一次文档采集会话；
- 支持拍照，以及后续的视频关键帧提取；
- 完成页面检测、裁边、旋转、透视矫正、质量判断和去重；
- 在稳定相机预览上管理候选页，允许查看、删除、重拍和调整顺序；
- 按稳定 `pageId` 与对应内容身份可靠上传页面，接收成功后立即排入该页 OCR 队列；
- 点击完成时发起最终页序与有效版本提交，显式触发未来会话级 `finalize`；
- 展示服务端处理状态并接收最终文档生成物。

### Capture2Doc Server

- 接收工具按 `pageId` 提交的页面和采集元数据；
- 每页到达后立即排入 OCR 队列并保存与 `pageId` 绑定的结果；
- 接受最终提交并等到所引用页面的有效 OCR 结果齐备后，严格按确认顺序运行 VLM 与 C2D-XML 校验；
- 从通过校验的 C2D-XML 生成目标文档；
- 不承担宿主 App 的聊天会话管理，除非后续单独设计统一服务协议。

聊天模型服务和 Capture2Doc 本地服务是两个独立边界。当前不假设它们使用相同模型、进程、鉴权或部署设备。

## Android 架构基线

初始工程采用：

- Kotlin、Jetpack Compose 和 Material 3；
- 单 Activity 作为宿主；
- 状态向下、事件向上的单向数据流；
- Screen-level ViewModel 对外暴露不可变 UI State；
- Repository 作为 UI 与本地/远端数据源之间的边界；
- 普通前台异步任务使用 Kotlin Coroutines；
- 未来需要跨进程恢复的上传和同步任务以 WorkManager 为既有架构方向，尚未接入，具体调度规则待设计；
- 扫描会话、页面元数据和上传状态最终以本地持久化数据为事实来源；
- 图片文件与结构化元数据分开保存，不把大图放进 ViewModel 或导航参数。

当前已接入 CameraX、screen-level ViewModel、本地扫描草稿和临时导航。网络库、上传调度、task/对话模型和服务端 API 尚未接入；这些能力应在对应功能进入当前里程碑时再引入，不为 UI 原型预装完整技术栈。

## 初始代码边界

第一阶段保持单个 `:app` Gradle 模块，但按功能边界组织 package：

```text
app
├── feature/chat
├── feature/tools
├── feature/capture2doc
├── core/model
├── core/ui
├── data/conversation
└── data/capture2doc
```

当聊天、扫描、图像处理和可靠上传的接口稳定后，再根据高内聚、低耦合原则拆分 Gradle 模块。当前不复制大型项目的多模块数量，也不为每个操作机械建立 Use Case 或接口。

## 工具集成原则

宿主 App 与工具之间需要一个稳定但足够小的概念契约：

- 启动上下文：工具从哪个会话或入口打开；
- 生命周期：未开始、执行中、需要用户处理、完成、失败或取消；
- 结果：工具生成的文件及其类型、显示名称和本地引用；
- 返回动作：插入当前会话、打开预览或保存；
- 恢复：App 被系统回收后仍能从持久化状态恢复任务。

该契约不直接暴露 CameraX、Room、HTTP DTO 或具体模型类型。确切 Kotlin 数据结构应等第一个工具闭环明确后再冻结。

## Android 视觉主题基线

## 前置技术探针：CameraX 拍照

在对话式应用外壳之前先完成一个边界明确的 CameraX 探针，通过 Android 真机验证权限、4:3 取景、拍照、方向处理和文件尺寸。探针保留原始 JPEG，并生成不裁剪、不拉伸、最长边不超过 1280 像素的 JPEG OCR 派生图。该像素规格独立于 PaddleOCR 的 image-token 上限，模型侧仍由 processor 的 `max_pixels` 控制最终输入预算。

该探针不冻结最终导航、扫描 UI、页面模型或工具结果契约。实现说明见 [Android 相机架构与状态管理](android_camera_architecture.md) 和 [Android 相机拍摄与图像处理](android_camera_capture.md)，验收方法见 [Android 相机测试与验收](android_camera_testing.md)。

## 当前已实现里程碑：沉浸式拍照页

本轮已经完成拍照页 UI 和本地候选行为改造，未接入聊天模型、Gradio 或服务端：

1. 相机预览作为固定 4:3 底层，不因候选出现或状态变化而缩小；
2. 顶部仅保留返回按钮，移除“相机能力测试”和所有调试指标；
3. 圆角方形候选条悬浮在快门上方，并展示整个本地草稿的当前顺序；
4. 单击候选查看大图、双击永久删除、长按拖拽排序；
5. 快门固定在底部中央，“完成”固定在右侧；
6. 原图全部安全落盘后允许完成，1280 派生图可继续在后台生成；
7. 本轮“完成”暂时进入现有页面整理页，作为未来 finalize/task 返回流程的本地替身。

拍照页候选采用无文字状态反馈：处理中显示小型进度环，失败显示红色标记，页码只表达当前顺序。双击删除不提供二次确认或撤销；仍处于 `CAPTURING` 的页面不可删除，已经失败或等待重拍的占位可以删除。拖拽只在松手后持久化。横竖屏均使用同一套 overlay 锚点，不恢复旧的横屏侧栏。派生图处理失败但原图已经安全落盘时仍允许进入页面整理；原图缺失、损坏或仍在落盘时才阻止“完成”。

扫描草稿表达草稿身份、创建与更新时间以及有序页面引用。页面具有稳定 `pageId`、原图与派生图的本地引用和处理状态；数组位置是唯一页序。未来 OCR 需绑定同一页面的有效内容版本，最终提交表达页面集合、顺序与对应版本，不能把“只传 ID 数组”视为已经完整冻结的请求体。这些是采集与任务内部元数据，不进入公开 C2D-XML，也不把文件本身放进导航参数。

该里程碑不包含聊天 UI、真实模型调用、账号与云同步、页面上传、`finalize`、服务端进度轮询、自动文档检测、透视矫正、质量判断、去重或视频取帧。

## 后续里程碑：逐页 OCR 与文档任务

已决定的时序是：关联文档 task/session，载荷就绪后逐页上传，成功接收即排 OCR，完成时发起最终有序页面集合提交，所需结果齐备后再组装。排序不重跑 OCR，重拍必须匹配新内容结果，删除页不进入最终集合。入队不保证立即占用 GPU；任务页显示真实阶段。协议与异常案例统一见 [扫描 Pipeline](capture_pipeline.md)。

当前“保存并退出”只保留本地文件。联网后部分页面可能已上传或识别，退出弹窗、暂停/恢复、放弃草稿与服务端资产清理需要随会话设计迁移；不能直接复用“尚未上传”的提示。当前单草稿策略也不自动决定未来宿主任务数量。独立整理页中的重拍等操作如何迁入目标相机流程、已完成文档如何创建新修订，仍需产品设计。

## 后续里程碑：对话式应用外壳

扫描草稿闭环稳定、聊天模型服务具备联调条件后，再实现对话首页、消息流、输入区、工具入口和 Capture2Doc 结果返回。届时先使用足够小的工具契约连接现有扫描流程，再决定聊天 Provider、账号和会话持久化方案。
